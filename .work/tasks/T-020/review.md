`make check`: green (20 scripts, 0 failed, smoke_io.py 1.90 s). The total runtime was 61.99 s, which is over the policy's 60 s budget (see LOW item).

[HIGH] src/voiceroom/io.py:189-197 (also WavSink 243-249): each `AudioOut` chunk goes through `resample_poly` on its own, with no filter state carried between chunks. The FIR sees zeros past every chunk edge, so each boundary gets a transient. → Failure: the OpenAI path sends 24 kHz chunks, and on a 48 kHz (macOS default) or 44.1 kHz output device every chunk boundary distorts. I measured this: a 0.5-amplitude 440 Hz sine in 20 ms chunks, 24k->48k, differs from whole-signal resampling by up to 0.24 at each boundary. That is an audible click/buzz every chunk on every live reply. WavSink has the same problem whenever its rate differs from the provider's. → Fix: use a stateful streaming resampler (e.g. `soxr.ResampleStream`, or keep the filter tail/overlap between calls), reset it on interrupt or on a new reply_id. Another option is to open the OutputStream at the provider rate and let PortAudio/CoreAudio convert. Add a smoke check that chunked output matches whole-signal resampling within a tolerance.

[MEDIUM] src/voiceroom/io.py:156,199-209,225: `_played` is only reset in `interrupt()` and never at the start of a new reply. → Failure: reply 1 plays out in full (5 s). During reply 2 the owner barges in after 1 s, and `interrupt()` returns ~6000 ms. T-022 passes this as `audio_end_ms` to `conversation.item.truncate`, OpenAI rejects it because it exceeds the item's audio duration, and the transcript is not truncated. → Fix: track `reply_id` from `AudioOut` and reset `_played` when a new reply_id first reaches the device. It should also count per reply, not per write.

[MEDIUM] src/voiceroom/io.py:189-205: `write()`/`play()` ignore `AudioOut.reply_id`, but the base contract says consumers should drop ids <= the last interrupted one. → Failure: on barge-in, `interrupt()` clears `_buf`, but the remaining chunks of the cancelled reply are still in the provider's `audio_out()` queue. `play()` writes them right away, so the cancelled reply keeps playing. → Fix: have `interrupt()` record the current reply_id, and make `write()` drop chunks with `reply_id <=` that value.

[MEDIUM] src/voiceroom/io.py:109-117: MicSource always opens the InputStream at 16 kHz with no fallback. → Failure: on Linux/ALSA `hw:` devices and many USB mics that only support 44.1/48 kHz, `InputStream(samplerate=16000)` raises `PortAudioError: Invalid sample rate`, so `voiceroom enroll` and `demo` can't use the mic. → Fix: if 16 kHz fails (or always), open at the device's `default_samplerate`, then resample to 16 kHz with a stateful resampler and re-frame to `frame_size` before queueing.

[MEDIUM] scripts/smoke/smoke_io.py (whole file): MicSource has no runnable proof. Nothing in the smoke covers the PortAudio-thread -> loop handoff, drop-oldest on a full queue, or the stop sentinel. sounddevice isn't installed, so the only live-path code that runs is the `list_devices()` except branch. → Failure: a regression in `_callback`/`_put`/`stop()` (e.g. the sentinel getting dropped, or the loop being captured wrongly) ships unnoticed until the human's live test. → Fix: put a fake `sounddevice` module in `sys.modules` (an InputStream whose `start()` launches a thread that calls the callback N times). Then assert that N frames of 512 come out, that iteration ends after `stop()`, and that `dropped` > 0 when the consumer stalls.

[LOW] src/voiceroom/io.py:139-141: if a MicSource is iterated without `start()`/`async with`, `_frames()` waits on an empty queue forever. → Failure: `await pipe.run(MicSource())` hangs silently and never reports an error. → Fix: raise in `_frames()` if `_stream is None`.

[LOW] src/voiceroom/io.py:126-128: the `status` argument (input overflow) is ignored, and if the loop has closed while the stream is still running, `call_soon_threadsafe` raises `RuntimeError` on the PortAudio thread. → Failure: overflows are invisible when diagnosing choppy identification, and a crash path that skips `stop()` produces PortAudio callback tracebacks. → Fix: count `status.input_overflow` into `dropped`, and wrap the hop in try/except RuntimeError.

[LOW] src/voiceroom/io.py:186-187,168-169: `sr` falls back to 16 kHz before `start()` sets the device rate. → Failure: audio written before `start()` is resampled to 16 kHz and then played at 48 kHz, i.e. at 3x speed and higher pitch. → Fix: query the rate in `__init__`, or refuse `write()` before `start()`.

[LOW] src/voiceroom/io.py:65-66: an ndarray source is assumed to be 16 kHz mono with no check, and a 2-D array makes `iter_frames` raise. → Failure: a caller passing a 48 kHz or stereo array gets 3x slowed audio or a ValueError. → Fix: accept `sample_rate=` and apply `to_mono`/`resample` for array inputs.
