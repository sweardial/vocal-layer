# Review T-045: LiveKitRoom transport

Scope: `src/voiceroom/adapters/livekit_room.py` and `scripts/smoke/smoke_livekit_room.py` (both untracked). `make check` is green. I ran it twice. The second run had one unrelated flaky FAIL in `smoke_io.py` ("turn dropped: identify_error"), and it passed when rerun alone. `smoke_livekit_room.py` passed 3 times out of 3 standalone (about 6.2 s, budget 15 s). It is not a trivial pass: the binary and extra are present, it reports 4 turns labelled synth000/synth001/synth000/synth001, and the listener hears 5.7 s of reply. The claimed identity through the `voiceroom_user` attribute is really exercised: the `verified` TrackPolicy raises if the claimed identity is not a member, so `device-7` would fail the run. Credentials are kept out of `repr` and error messages. Dev keys are used only for localhost. Provider code stays inside `adapters/`.

No HIGH findings.

[MEDIUM] src/voiceroom/adapters/livekit_room.py:33,198-206: the per-track queue drops the oldest audio with no signal at all → if the pipeline falls behind for a few seconds (for example wespeaker on a slow Mac with 3 participants, or a GC pause), audio from the middle of an utterance is thrown away. The turn is then spliced, and the source's frame-count room clock falls behind the other sources (see the T-0xx room-clock follow-up), so commit order and turn times go wrong. Nothing is logged, so this can't be diagnosed. The comment is also wrong: AudioStream yields 10 ms frames, so 500 chunks hold about 5 s, not about 10 s. → Count the dropped samples for each track. Emit a rate-limited warning that contains only the participant sid and the dropped ms, never audio. Correct the comment, or size the queue in samples.

[LOW] src/voiceroom/adapters/livekit_room.py:92-110: `connect()` does not clean up after a partial failure → if `r.connect` succeeds and `publish_track` then raises or times out, the Room is left connected with event handlers attached. `RoomAgent.run` calls `transport.connect()` outside its try/finally, so `close()` never runs. The bot stays in the room as a zombie participant, and any track_published events trigger subscriptions and pumps until the process exits. → Wrap the code after `r.connect` in try/except. On failure, call `await self.close()` and then re-raise.

[LOW] src/voiceroom/adapters/livekit_room.py:166-179: there is one resampler per sample rate, and it is only flushed or reset when a chunk has `final=True` → when a reply is cut off before its final chunk (barge-in, provider error), the resampler's lookahead state (a few ms of the old reply) is carried into the start of the next reply. It causes a click or splice. This only affects providers whose rate is not 24 kHz (MockProvider runs at 16 kHz; OpenAI at 24 kHz is passthrough). → Track `audio.reply_id` and reset the resamplers when it changes. T-047 should rely on the same reset.

[LOW] src/voiceroom/adapters/livekit_room.py:181-195 / scripts/smoke/smoke_livekit_room.py:145-147: teardown leaves FFI handles live → every passing run of this smoke prints 10 `FfiHandle.__del__ ... assert dropped` tracebacks and "Attempted to drop unknown FFI handle" lines to stderr. The T-044 loopback smoke prints none. D-018 says this means handles were not torn down before the loop ended. In `voiceroom room` (T-048), every shutdown will dump tracebacks that hide real errors. The smoke ignores stderr, so the problem stays invisible. → In `close()`, unpublish the local track (`local_participant.unpublish_track`) before disconnecting. Make sure each pump's AudioStream is closed before `room.disconnect()`. Have the smoke check that the child's stderr does not contain `FfiHandle`.
