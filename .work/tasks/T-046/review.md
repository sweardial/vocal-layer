# T-046 review (sessions, invites, membership-driven policy)

`make check`: green (34 scripts, 0 failed, 33.6 s; smoke_sessions.py PASS 2.55 s, offline).

What holds up: the invite MAC check uses a derived subkey and `compare_digest`. Every parse failure becomes one `InviteError`. Expiry is MAC-protected. The single-use nonce is consumed under a thread lock plus flock. Session files are Fernet-encrypted, written atomically with mode 0600, and named by keyed hash. No code, token or embedding is logged. The provider-specific kick lives in `adapters/`. `deliver_gate` catches a turn that was queued before a revoke.

## Findings

[HIGH] src/voiceroom/sessions.py:346-355 (with src/voiceroom/adapters/livekit_room.py:62-67, sessions.py:245-252): revoke only removes participants that have an audio **source** in the pipeline, and join tokens never expire early. → Bob gets a join token, then the owner revokes him. `make_token` sets no TTL, so the LiveKit SDK default of 6 h applies, and the grant includes subscribe. Bob reconnects with the same token without publishing a mic, or just stays connected muted. He never becomes a `pipeline.sources` entry, so `sync_once` never kicks him. For up to 6 h he keeps hearing every member's audio and the bot's replies. If he does publish, he is kicked about every 0.5 s and rejoins straight away. The accept criterion says "the participant is removed", and that holds only for publishing participants in FakeRoom. → Fix: give `join_token` a short TTL (minutes). Drive kicks from the transport's participant roster (`RoomAgent._joined` / ParticipantJoined), not from `pipeline.sources`. Kick by the real LiveKit identity. Keep a revoked set so a reconnect is kicked as soon as ParticipantJoined arrives. Optionally mint member tokens via a short-lived refresh that checks membership again.

[MEDIUM] src/voiceroom/sessions.py:142 (also used under the lock at 190, 216, 236): the `get()` cache key is `(st_mtime_ns, st_size)`. Linux sets mtime from the coarse clock (ms granularity), HFS+ and some bind mounts have 1 s granularity, and Fernet output is padded to 16 B blocks, so a revoke (removing `, "bob"`, 7 B) often keeps the same size. → The long-running agent's store caches the session. A CLI `revoke` lands within the same mtime tick with an unchanged size. `SessionPolicy._policy`, `_allowed` and `sync_once` keep serving the old member list indefinitely, so the revoked member stays forwarded. Because `invite`/`accept`/`revoke` also read through this cache inside `_locked()`, a stale instance can write an old record back. That loses the update: a consumed nonce comes back (invite reuse) or a revoke is undone. → Fix: add `st_ino` to the stamp (`os.replace` always creates a new inode) and `st_ctime_ns`. Under `_locked()`, always read from disk and skip the cache.

[MEDIUM] src/voiceroom/sessions.py:349 (with src/voiceroom/rooms/runner.py:98): `sync_once` kicks any source whose claimed identity is not a member, not only revoked ones. On LiveKit, `claimed = attributes.voiceroom_user or info.identity`, and LiveKit identities are never empty, so `claimed` is never None there. → A collaboration session with `unknown="label"` has a shared room device or a browser test client with identity `guest-1`. That participant is kicked within 0.5 s instead of being labelled Unknown, so the `TrackPolicy("shared", ...)` branch (sessions.py:302) and the session's unknown policy can never run on LiveKit. Session tests are also exposed: kicking every non-member falls into the same path as revocation. → Fix: kick only identities that were members and got revoked (track the revoke set or the previous member snapshot). Leave never-members to SessionPolicy and the unknown policy. If kicking strangers is intended, write that down in decisions.md and make it a session option.

[MEDIUM] src/voiceroom/sessions.py:350-355: the source is removed from the pipeline before the kick, and a failed kick is never retried. → Example: the LiveKit server is unreachable, or the key lacks the roomAdmin grant. The participant stays connected and keeps publishing. `pipeline.sources` no longer holds it, so later `sync_once` calls skip it. Its `_pump` keeps decoding audio into a queue nobody reads and logs "pipeline behind, dropped old audio" on every frame (livekit_room.py `_pump`). The result is unbounded log spam and wasted CPU for the rest of the session, and the revoked user stays in the room. → Fix: keep pending-kick ids and retry each sync until a ParticipantLeft arrives. Discard the track (runner `_discard`) instead of leaving the iterator unread.

[LOW] src/voiceroom/sessions.py:353, src/voiceroom/adapters/livekit_room.py:247-250: the kick passes `src.claimed` as the LiveKit identity, but `claimed` can come from the `voiceroom_user` attribute, which may differ from the participant identity. → Example: a token minted outside `join_token` has identity `x` and `voiceroom_user=bob`. After bob is revoked, `remove_participant(identity="bob")` fails with not found, or removes the real bob's other connection, and `x` stays. → Fix: carry the transport identity (ParticipantJoined.identity) and kick by that.

[LOW] src/voiceroom/sessions.py:353, 357-360: the `await self.kick(...)` HTTP call has no timeout, and any exception other than one raised by the kick (for example `StoreKeyError` from `get`) ends `run()` silently. → A hung RoomService call blocks every later `sync_once`, so later revokes are never applied to the pipeline. → Fix: wrap with `asyncio.wait_for(…, timeout)` and catch/log (without details) per iteration in `run()`.

[LOW] scripts/smoke/smoke_sessions.py:253, 76-77: the log check passes trivially and coverage has a gap. The module logs nothing except the kick-failure line, and the check looks for only one code, never the join token or later codes. The accept-time enrollment re-check (sessions.py:222-225, consent withdrawn or signature deleted after invite) is never exercised. → A regression that logs a token, or drops the accept-time check, would still pass. → Fix: assert that none of `code`, `late` and `tok` appear in the captured logs or exception strings. Add one case: invite bob, delete his signature or withdraw consent, then `accept` → `InviteError`.
