# T-019 review (OpenAI Realtime adapter)

`make check`: green (16 smoke scripts, smoke_openai_adapter.py 2.6 s, offline). websockets 15.0.1 installed.
The API key handling is fine. The key is read from env, not in `repr`, and websockets handshake debug logs go to a non-propagating NullHandler logger. The smoke check confirms this with root logging at DEBUG.

## Findings

[HIGH] src/voiceroom/adapters/openai_realtime.py:122-150: `send_turn` sends `response.create` even when a response is already in progress (`_active`/`_awaiting` set) → The pipeline (pipeline.py:224) sends every accepted turn without waiting for the previous reply. In collaboration mode alice speaks, the model starts replying, and bob's turn is accepted. The real API rejects the second `response.create` with `conversation_already_has_active_response`, which the adapter only logs (line 231), so bob's turn never gets a reply. Worse, `_awaiting` was incremented (line 149) and is never decremented because no `response.created` arrives. The next `interrupt()` then does `_drop_next += 1` (line 160), and the next legitimate reply is silently dropped (line 207-209). After that every idle `interrupt()` also sends a spurious `response.cancel`. The fake server (fake_realtime_server.py:49-52) allows concurrent responses, so the smoke check cannot catch this. → Fix: in `send_turn`, if a response is active or awaited, either cancel it first (barge-in semantics) or wait for its `response.done` before sending `response.create`. Tag `response.create` with a client `event_id` and, on an `error` whose `event_id` matches, roll back `_awaiting`. Make the fake server return `conversation_already_has_active_response` when a response is live, and add that case to the smoke script.

[HIGH] src/voiceroom/adapters/openai_realtime.py:156-157: `interrupt()` returns early when no response is in progress, so `conversation.item.truncate` is never sent once `response.done` has arrived → The API generates audio faster than realtime, so `response.done` usually arrives seconds before local playback ends. Barge-in (T-022) happens during playback, and by then `_active is None and not _awaiting`, so nothing is sent. The model's context keeps the full reply the user never heard. Truncate exists for exactly this case, and the plan says truncate is sent "only if `played_ms is not None` and an item exists", without requiring an active response. The smoke script (smoke_openai_adapter.py:88-91) asserts "idle interrupt sends nothing" and so locks the bug in. → Fix: gate only `response.cancel` on active/awaiting. Send the truncate whenever `played_ms is not None` and `_item` is set and has not been truncated yet. Clear `_item` when a new turn is sent, so a stale item from an older reply is never truncated. Add to the smoke script: wait for `final`, then call `interrupt(50)` and assert one truncate and no cancel.

[MEDIUM] src/voiceroom/adapters/openai_realtime.py:152-172: `interrupt()` does not purge chunks of the cancelled reply already queued in `_q` → The Provider contract (base.py `audio_out` docstring) says "Adapters must not yield chunks of a reply cancelled by interrupt()", and MockProvider drains its queue (mock.py:58-63). Here the deltas arrive faster than realtime while the sink reads at playback pace, so seconds of cancelled audio sit in `_q` and are yielded after the interrupt. A consumer written against MockProvider's behavior (T-022) keeps playing the reply over the barge-in. → Fix: in `interrupt()`, drain `_q` of chunks whose `reply_id` equals the cancelled reply, keeping any `None` sentinel. Or use one shared rule, "consumer drops reply_id <= interrupted", and make MockProvider match it.

[MEDIUM] src/voiceroom/adapters/openai_realtime.py:228-229: a `final=True` chunk is emitted only for `status == "completed"` → A response that ends `failed` or `incomplete` (content filter, `max_output_tokens`, server error) never gets a final chunk. Any consumer that waits for `final` to mark the end of the reply stays in "responding" state. scripts/live/openai_realtime_check.py:36-43 waits 60 s and then raises TimeoutError without calling `close()` or saving anything. → Fix: emit a final chunk for every non-dropped `response.done`, and log the status and `status_details.type` (never payloads).

[MEDIUM] src/voiceroom/adapters/openai_realtime.py:143-150: `send_turn` is not atomic under cancellation or encode errors → The pipeline wraps it in `asyncio.wait_for(..., send_timeout_s)` (pipeline.py:224). A timeout mid-loop leaves the attribution item and some `append`s in the server's input buffer with no commit. The next turn's commit then sends the stale partial audio together with the new turn, under the next speaker's label. If cancellation hits after `_awaiting += 1` (line 149) but before `response.create` goes out, the same `_awaiting` desync as in the first HIGH drops the next reply. Non-finite samples cause the same partial-send state, because `float_to_pcm16` raises ValueError inside the loop (line 146) after `conversation.item.create` was already sent. → Fix: check `np.isfinite` and encode all chunks before the first send. On exception or cancellation inside the lock, send `input_audio_buffer.clear`, and increment `_awaiting` only after `response.create` has been sent.

[LOW] src/voiceroom/adapters/openai_realtime.py:195-198: any malformed or unexpected server event (`ev["response"]["id"]` KeyError, a missing `delta`, an odd-length base64 delta → `np.frombuffer` ValueError) escapes `_handle` and kills the reader → The audio stream ends permanently, but `_ws` stays open, so later `send_turn` calls succeed and their replies are never read. → Fix: catch per-event exceptions in the loop (log only type and event name). On a fatal reader exit, set a flag so `send_turn` raises.

[LOW] src/voiceroom/adapters/openai_realtime.py:73-93: calling `connect()` twice does not close the previous socket or cancel the previous reader → On reconnect, the old reader keeps running and calls `_handle` on the shared state and `put_nowait(None)` on the old queue, and the old connection leaks. → Fix: call `close()` at the start of `connect()` if `_ws` or `_reader` is set.
