## Findings

[HIGH] src/voiceroom/rooms/runner.py:224-235: `room_task` failing is never noticed while the event loop is running. `RoomAgent.run` only awaits `room_task` after `transport.events()` ends. → If `provider.connect()` raises (OpenAI key or network failure, which is common), `RoomPipeline.run` dies. The agent still consumes room events and audio, adds sources and creates turns that are never committed. It reports nothing until the room ends, which never happens on a live LiveKit room. Reproduced: with a provider whose connect raises and `FakeRoom(realtime=True)`, `run()` was still going after 4 s with no error, and there was asyncio "Task exception was never retrieved" noise from `_decide`. T-048's CLI would stay in the room deaf and silent. → Fix: race the event loop against `room_task`. For example, iterate events in their own task and use `asyncio.wait({events_task, room_task}, FIRST_COMPLETED)`, or add a done-callback that cancels the event consumer. Re-raise the pipeline's exception and close the transport.

[MEDIUM] src/voiceroom/rooms/runner.py:243-245 and src/voiceroom/rooms/fake.py:136: an ignored `TrackAudio` (unknown or duplicate participant) is dropped without draining or closing its `frames` iterator. → FakeRoom's driver blocks forever on `await q.put` for that track once QUEUE_DEPTH fills, which stalls every participant. Reproduced: two FakeParticipants with the same id make `run()` hang (5 s timeout). On a live transport, an undrained per-track stream buffers without bound. → Fix: when ignoring a track, drain or `aclose()` its iterator in a background task. Have FakeRoom reject duplicate ids up front.

[MEDIUM] src/voiceroom/rooms/runner.py:243: a participant's new track is dropped while their previous source is still in `room.sources`. → In LiveKit, switching mic device or republishing ends the old track and immediately sends a new `TrackSubscribed`. If the new `TrackAudio` arrives before the old `_feed` task has seen end-of-stream and popped the source, the new track is ignored, and that participant is unheard for the rest of the session. → Fix: on a new track for a participant who already has a source, `remove_source` the old one (flushing it) and add the new one. Or key sources by (participant, track).

[MEDIUM] src/voiceroom/rooms/runner.py:195-197, 208-211: `_pump` has no error handling. → One transient `publish_audio` failure (for example a LiveKit `capture_frame` error during a reconnect) silently kills the pump. All later reply audio is never published, and the provider's `audio_out` queue grows without bound (MockProvider and OpenAI buffer without limit). The stored exception only resurfaces at `close()`, where `await self.pump` raises from inside `RoomPipeline.run`'s `finally` and masks the real shutdown path. Also, if the OpenAI reader drops and later reconnects, `audio_out` has already returned (`_push(None)`), so the pump is gone for good. → Fix: catch and log the exception type per chunk and keep the pump alive. Restart the pump on reconnect (or document that a provider reconnect needs a new pump). In `close()`, collect the pump's exception without re-raising it.

[MEDIUM] scripts/smoke/smoke_room_fake.py:42-48,68: the "leaves mid-turn" check passes without exercising `RoomAgent`'s `ParticipantLeft` → `remove_source` path. FakeRoom ends the track (`q.put(None)`) before it emits `ParticipantLeft`, so `_feed` usually reaches end-of-stream and flushes by itself, and `remove_source` is a no-op. → If the `ParticipantLeft` branch in `runner.py:231-233` were deleted or broken, the smoke would still pass. (The comment "during its second utterance" is also wrong: leaving at 2.0 s local is inside the first utterance, which runs from 1.0 to 3.5 s.) → Fix: make the FakeRoom leave path emit `ParticipantLeft` while the track is still open (end the track only after the event, or never end it for a scripted `leave_at`). Assert that pb's last record ends at about LEAVE_B and that its partial turn was flushed through `remove_source`.

[LOW] src/voiceroom/rooms/runner.py:247: no `t_offset` is passed, so room time comes from `RoomPipeline._room_now()`, which is the max stream time of the *current* sources. → If the room empties and someone joins later (for example a single user reconnecting after 5 min), their turns restart at room time 0. Records and latency lines (T-048/T-049) go backwards, and the bleed history `_seen` holds turns from an unrelated earlier epoch at the same times. → Fix: have RoomAgent keep a monotonic room clock (loop time since `connect`) and pass `t_offset` on `add_source`. This overlaps with the existing T-0xx capture-time follow-up.

[LOW] src/voiceroom/rooms/runner.py:246: the `voiceroom_user` attribute overrides the server-vouched participant identity. → In LiveKit, a participant whose token allows `canUpdateOwnMetadata` can set its own attributes and claim another member's identity, which selects whose signature and policy apply to its track. → Fix: document in `base.py` that transports must only pass attributes set by the token or server, or prefer `identity` and treat the attribute as valid only when the transport marks it trusted.

[LOW] src/voiceroom/rooms/base.py:1,66: the module docstring says "16 kHz mono float32 audio in both directions", but `publish_audio` receives provider `AudioOut` at its own `sample_rate` (24 kHz from OpenAI, per T-045). → A transport implementer who trusts the docstring would publish 24 kHz audio as 16 kHz, so it plays slow and low-pitched. → Fix: state that `publish_audio` must honor `audio.sample_rate`.

[LOW] src/voiceroom/rooms/fake.py:91 and runner.py:254: participant audio is not validated. → A stereo `(n, 2)` array passed to `FakeParticipant` makes `_reframe`'s `np.concatenate` raise. `_feed` then logs only "source failed" and the participant is silently dropped. Non-16 kHz arrays play at the wrong speed. → Fix: in `FakeParticipant.__post_init__`, check `ndim == 1` and cast to float32 (and document the 16 kHz requirement next to the check).
