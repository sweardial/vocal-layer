## Findings

[HIGH] src/voiceroom/pipeline.py:339: barge-in runs only in `_finish`, which means after `TurnEnd` (end of speech + 0.4 s end silence), after full-turn identification, and after `_continuity_ok`. It never runs at `IdentifyReady`, which is when the speaker is first confirmed. → Failure: the owner starts talking 2 s into a 10 s reply and speaks for 4 s. The reply keeps playing over them for the whole 4 s plus endpointing and scoring, and only then stops. If the reply ends before the owner does, `sink.active` is False and nothing is interrupted. So the reply is never cut while the owner is talking, which is what the goal asks for ("When an accepted speaker *starts* talking ... stop local playback"). Without headphones, the reply audio also leaks into the owner's turn the whole time, which lowers continuity scores and makes a wrong REJECT more likely. → Fix: fire barge-in from the early path. When the `IdentifyReady` task returns a match that `policy.decide(match, final=False)` accepts (or the first owner windows pass), call `_barge_in()` from a task spawned off the frame loop. The loop must not await the provider. Keep a per-turn flag so the interrupt fires at most once, and keep the `_finish` call as a fallback for turns with no early decision.

[MEDIUM] Makefile / scripts/smoke/run_all.py: `make check` is red because the smoke total is 86.8 s against a 75 s budget. The acceptance criteria require `make check` green. This diff adds about 3.8 s. The suite is over budget even without it (about 83 s), so the cause is mostly older, but the task cannot be accepted as-is. → Failure: the harness gate fails on this task. → Fix: get under budget. For example, shrink `smoke_bargein` (it builds a 3-speaker corpus and calibrates a threshold just to run two turns; reuse fixed synthetic segments), or open a follow-up to trim `smoke_identify_isolation.py` (about 16.9 s) and `smoke_cli.py` (about 13.8 s). Add the follow-up to the backlog rather than raising the budget silently.

[MEDIUM] src/voiceroom/io.py:329 (`SpeakerSink.active`): "active" means only "local buffer is non-empty", not "a reply is in progress". → Failure: the owner speaks while the model has started a response but its first audio delta hasn't arrived, or the 60 s buffer drained during a network stall between deltas. `active` is False, so `_barge_in` returns early, `provider.interrupt(played_ms)` is never called, and no `conversation.item.truncate` is sent. `send_turn` still cancels the response, but the conversation history now holds the whole assistant reply, including the part the user never heard. The model then answers as if the user heard all of it. → Fix: track reply state in the sink (e.g. `_latest > _cancelled` and the end-of-reply marker not yet played), or ask the provider whether a response is open. Then call `provider.interrupt(sink.interrupt())` whenever a reply is unfinished, even if the local buffer is momentarily empty.

[MEDIUM] scripts/smoke/smoke_bargein.py:43-62: the smoke proves the Pipeline calls a duck-typed `FakeSink`, but no new or changed production sink code runs. `FakeSink.active`/`interrupt` stand in for `SpeakerSink.active` (new) and the CLI's `sink=sink` wiring (new). `played_ms == 1234` is a constant from the fake. → Failure: a regression in `SpeakerSink.active` (e.g. it returns False while audio is queued) or a dropped `sink=sink` in `cmd_demo` would leave every smoke green while the real demo never barges in. → Fix: in the smoke, use a headless `SpeakerSink(sample_rate=16000)`. Set `_stream` to a dummy and drive `_callback` by hand to "play" part of a reply, then assert `provider.interrupts[0]` equals the played ms and `_buf` is empty. Optionally run `cmd_demo --provider mock` with a stub sink to check the wiring.

[LOW] src/voiceroom/pipeline.py:306: `provider.interrupt` gets its own `send_timeout_s` (5 s), and then `send_turn` gets another 5 s. The OpenAI `_cancel_locked` can wait `CANCEL_WAIT_S` = 5 s in each. → Failure: the server is slow to confirm `response.cancel`. The interrupt times out at 5 s and logs "barge-in failed". `send_turn` then waits up to 5 s more and drops the turn with `send_timeout`. The worker is serial, so every queued turn is delayed about 10 s, double the old worst case. → Fix: share one deadline across interrupt + send (e.g. `asyncio.timeout(self.send_timeout_s)` around both), or skip the provider call in `_barge_in` and let `send_turn`'s own cancel run, sending only the truncate.

[LOW] src/voiceroom/pipeline.py:302: barge-in reads sink state when the serial worker reaches the turn, not when the turn happened. → Failure: in `voiceroom demo --input x.wav` (unpaced) with a real `SpeakerSink`, turns queue up faster than real time. Each accepted turn flushes whichever reply happens to be playing at that moment, even if the turn was spoken before that reply existed. The user hears only fragments of replies. → Fix: compare the turn's `t_start` with when the current reply started (or disable barge-in for unpaced file input).
