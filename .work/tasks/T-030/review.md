## Findings

[HIGH] scripts/smoke/run_all.py:14,40: `WORKERS = 4` is fixed and ignores the CPU count. Each child process also starts up to 4 ORT intra-op threads (`N_THREADS` uses `os.cpu_count()`, which ignores the CPU affinity mask). Timing assertions inside the smokes therefore fail when the scripts compete for CPU. → Reproduced twice with `taskset -c 0-1 uv run python scripts/smoke/run_all.py`: `FAIL smoke_pipeline_real.py` at `assert max(st.commit_latencies) < 2.0` (line 43; script took 13.8-14.6 s, total 54-55 s). The same script run alone on the same 2 CPUs passes in 6.8-7.2 s. So `make check` goes red on a 2-core CI runner or laptop VM only because of this change. The suite also sits close to the 60 s budget there. → Fix: size the pool from the CPUs actually available (`len(os.sched_getaffinity(0)) // 2`, at least 1). Run the timing-sensitive smokes (smoke_pipeline_real, smoke_identify_isolation, smoke_bargein, smoke_cli) serially after the parallel batch, or set `OMP_NUM_THREADS`/an `N_THREADS` override of 1 in the child environment. Better still, also do what the backlog asks: shorten smoke_identify_isolation (now 18 s, was 15 s) and smoke_cli (22 s under contention), so the serial total fits the budget without depending on core count.

[MEDIUM] src/voiceroom/bench/pipeline.py:286,312: `--jobs` defaults to 4, so the isolation passes, which feed the headline "commit latency p95 vs 700 ms: MEETS/MISSES" verdict, run alongside 3 other realtime pipelines in the same process. They share the GIL (Python fbank frame loop, VAD and the event loops) and oversubscribe ORT (4 passes x 4 intra-op threads). `compute_s` is wall time, so all of that contention lands in the latency figure. → Measured here on 8 cores: compute p95 rose from 34 ms to 52 ms and commit p95 from 412 ms to 430 ms. On a 2-4 core host the inflation grows, and the verdict can flip to MISSES even though production runs one pipeline per process. The verdict now depends on `jobs` and the host, and reports are no longer comparable with earlier ones (all made with jobs=1). → Fix: run the isolation passes with jobs=1 and overlap only the collaboration passes, or overlap only enrollment and corpus loading. Otherwise, when jobs>1, print latency as "not measured (jobs>1)" and keep the verdict for jobs=1 runs. At a minimum, divide ORT intra-op threads by `jobs`.

[MEDIUM] src/voiceroom/bench/pipeline.py:256-297: nothing runnable exercises the new code (the signature cache, the threaded `build`, `--jobs`). No smoke calls `build()`; smoke_pipeline_real imports only `stream`/`score_isolation`. No summary.md or regenerated report shows that the bench takes under 5 min. → If a later edit breaks the futures/`jobs_list` pairing (for example, scoring the isolation result against the wrong conversation), `make check` stays green and the next bench report is silently wrong. → Fix: in smoke_pipeline_real (or smoke_windows_bench), call `build(CappedCorpus(...), emb, n_conv=2, n_turns=2, ..., speed=6, jobs=2)`. Assert that 2 conversations were scored, owner FR is 0 and attribution is above a floor, and that a repeated speaker is enrolled only once (count calls on a wrapped embedder). Record the bench wall time in summary.md.

[LOW] src/voiceroom/bench/pipeline.py:286-297: an exception from one pass reaches the caller only when `with ThreadPoolExecutor` exits, which waits for every queued realtime pass. → With `--conversations 14 --speed 1`, a failure in conversation 1 (for example the `assert len(committed) == len(provider.turns)` in score_collab, or a missing VAD model) shows its traceback only after all remaining passes finish, which takes minutes. → Fix: on exception, call `pool.shutdown(cancel_futures=True)` before re-raising, or use `try/except` around the scoring loop that cancels pending futures.

[LOW] scripts/smoke/run_all.py:13: the backlog goal says "shorten the slowest smokes", but the change only adds parallelism and lowers the budget from 90 to 60 s of wall time. No slow smoke was trimmed (smoke_identify_isolation went from 15 s to 18 s under contention). → Every new smoke adds about 1/WORKERS of its own time to the wall budget, plus contention for the others, so the margin problem T-030 was meant to fix comes back once the suite runs on fewer cores (see the HIGH finding). → Fix: trim smoke_identify_isolation (e.g. lower the `identify_timeout_s` values and use shorter frozen-child waits) as the task asked, independently of the parallel runner.
