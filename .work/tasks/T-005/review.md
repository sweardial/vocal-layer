## Findings

[MEDIUM] src/voiceroom/store.py:101-109: load() does not check that the decrypted record's `name` matches the requested name, and Fernet is not bound to the filename → Anyone with write access to the store dir (no key needed) can copy mallory's `.sig` over sha256("alice").sig. `load("alice")` then returns mallory's embeddings with no error. Verified: `list()` gives `['mallory','mallory']`. In isolation mode, an owner lookup would then load the wrong voiceprint, or a caller that trusts the requested name would accept mallory as owner. → Raise StoreError when `rec["name"] != name` in `_record`, and have list() flag duplicates or mismatches against `_path(rec["name"])`.

[MEDIUM] src/voiceroom/store.py:67: Filenames are unsalted sha256(name), but the comment says they "don't reveal who is enrolled" → An attacker with read access can hash candidate names ("alice", "Alice", employee directory) and confirm who is enrolled. For biometric data under BIPA/GDPR, that membership is itself sensitive. → Derive the filename with HMAC-SHA256 keyed by a subkey of the store key (or use random IDs plus an encrypted index).

[MEDIUM] src/voiceroom/store.py:117: list() decrypts every `*.sig` and raises on the first one it cannot read → One corrupt, truncated, or old-key file (for example after a crash, see below, or after ~/.voiceroom/key was lost and load_key silently made a new key) makes list() raise StoreKeyError for the whole store. Verified with a garbage `.sig`. The user then can't enumerate or clean up the good signatures, and since filenames are hashed they can't tell which file belongs to whom. → Skip unreadable files with a warning that names only the filename (or return them in a separate "unreadable" list), and keep the hard error for load().

[LOW] src/voiceroom/store.py:35-41: The keyfile is created with O_EXCL and only then written; an existing keyfile is read back without validation → If the process is killed between create and write, or a second process reads during that window, the keyfile is empty forever. Every later run then fails with "invalid key" and never regenerates. Verified: an empty keyfile gives `StoreKeyError: invalid key`. A pre-existing keyfile with mode 0644 is also used silently, and `~/.voiceroom` is created with umask defaults (typically 0755). → Write to a 0600 temp file, fsync, then `os.link`/rename into place. Raise a clear error naming the path if the keyfile is empty or malformed. Warn or refuse if `st_mode & 0o077`. Create the parent with mode 0o700.

[LOW] src/voiceroom/store.py:90-93: There is no fsync of the temp file before os.replace, and no fsync of the directory → After a power loss, the `.sig` can be zero-length. It then reads as "wrong key or corrupted file", and with the list() behaviour above it breaks the whole store. → Call `f.flush(); os.fsync(f.fileno())` before replace and fsync the directory fd after. Concurrent saves of the same name also share one `<hash>.tmp`; use `tempfile.mkstemp(dir=root)` instead.

[LOW] src/voiceroom/store.py:78-87: D-006 requires "embedder name/version", but the record stores only `sig.embedder` (a name) and has no record format version → If the model behind a registered name changes (for example a re-exported WeSpeaker ONNX in T-006 under the same `wespeaker-resnet34` name), old signatures load without error and are scored in an incompatible embedding space. Owners then get silent false rejects. There is also no `"v"` field to migrate the schema later. → Add `"format": 1` and an embedder version/model hash (add `version` to the Embedder protocol or pass it into save). Have load() or the matcher refuse a mismatch.

[LOW] scripts/smoke/smoke_store.py:41-42: Two assertions pass trivially. Raw float32 bytes would never appear in the file even if it were plaintext JSON, because the store base64-encodes them. And `str(sig.centroid[0])` is checked against reprs that are hand-written to omit arrays → If encryption were removed, only the `b"Zebediah"` check (line 40) would catch it, so the embedding-leak claim isn't proved on its own. → Also assert that `_b64(sig.centroid)` (the base64 form) is not in `raw`, or that `raw` starts with the Fernet token prefix `gAAAAA` and that `json.loads(raw)` fails.
