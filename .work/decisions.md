# Decisions

## D-001 (2026-10-08) How we prove changes while unit tests are off
- What: Every feature gets one smoke script in `scripts/smoke/`. Smoke scripts run offline on *synthetic voices* (`voiceroom.synth`) with a numpy-only `toy` embedder and an `EnergyVAD`. Checks that need real models or LibriSpeech print `SKIP: <reason>` and exit 0 when the assets are missing from `models/` or `data/`. Assets are fetched only by `scripts/fetch_models.py` and `scripts/fetch_data.py`, never by `make check`.
- Why: `make check` must be offline, fast (< 60 s), and green from a clean checkout. Real-model accuracy is measured by `make bench`, not by smoke scripts.
- Alternatives: commit small audio fixtures (not allowed: no audio in git); download in checks (not allowed: no network).

## D-002 (2026-10-08) Speaker-embedder candidates
- What: Pluggable `Embedder` protocol. Candidates:
  1. **WeSpeaker ResNet34-LM, ONNX** (`Wespeaker/wespeaker-voxceleb-resnet34-LM`, `voxceleb_resnet34_LM.onnx`, about 26.5 MB, CC-BY-4.0 so attribution is required, Vox1-O EER about 0.72–0.87 %). It runs on `onnxruntime` (1.30 has cp312 wheels) with an 80-dim Kaldi fbank front end. Use `kaldi-native-fbank` if it has a cp312 wheel, otherwise a numpy port. The implementer must verify the fbank config against the model's wespeaker config.
  2. **SpeechBrain ECAPA-TDNN** (`speechbrain/spkrec-ecapa-voxceleb`, Apache-2.0, about 83 MB, EER about 0.8 %). It is an optional extra `ecapa` because it needs torch (CPU wheels via the uv index). Known risk: torchaudio ≥ 2.9 breakage in speechbrain (`list_audio_backends`, issue #3012). Pin compatible torch/torchaudio versions and load audio with soundfile ourselves.
  - Possible third: 3D-Speaker CAM++ ONNX (unverified weights/licence). It is only a follow-up if the first two miss the targets.
- Why: WeSpeaker ONNX avoids torch at runtime and is small, which suits CPU realtime. ECAPA is the strong, well-known baseline.
- Final choice and threshold: decided by `make bench` in T-012 and recorded below.

## D-003 (2026-10-08) VAD
- What: Silero VAD as ONNX through `onnxruntime` directly (no torch). The model file is fetched by `scripts/fetch_models.py`. Frames are 512 samples (32 ms) at 16 kHz, and the implementer must verify this against the silero code. An `EnergyVAD` with the same interface is used for synthetic smoke checks.
- Why: Silero is the de-facto CPU VAD, and the ONNX path keeps torch out of the core install.
- Alternatives: webrtcvad (weaker, unmaintained wheels), and the `silero-vad` pip package (pulls in torch).

## D-004 (2026-10-08) Audio formats and libraries
- What: Internally, audio is **16 kHz mono float32 numpy** in [-1, 1]. int16 PCM is used only at I/O and provider boundaries. File I/O uses `soundfile` (wheels bundle libsndfile). Resampling uses `scipy.signal.resample_poly`. Mic/speaker use `sounddevice` (PortAudio is bundled on macOS and is `libportaudio2` in the container). It is imported lazily so that headless environments work.
- Why: These are few, standard, wheel-available dependencies.

## D-005 (2026-10-08) Evaluation data
- What: LibriSpeech **dev-clean** (SLR12, 337 MB, 40 speakers). `scripts/fetch_data.py` downloads it with mirror fallback (openslr.trmal.net, openslr.elda.org, us.openslr.org), verifies it against `md5sum.txt`, and extracts it to `data/LibriSpeech/`. `--mini` uses dev-clean-2 (SLR31, 126 MB) for quick runs. Noise is synthetic (white, pink, or brown at a target SNR).
- Why: dev-clean is small and has enough speakers for EER. MUSAN is 11 GB. ESC-50 is about 600 MB and CC BY-NC.

## D-006 (2026-10-08) Signature store
- What: There is one file per signature, encrypted with `cryptography` **Fernet** (authenticated). The key comes from `VOICEROOM_KEY`, or from a keyfile (default `~/.voiceroom/key`, created with mode 0600, never in the repo). Each record holds the embeddings, the embedder name/version, consent info and a timestamp. It never holds raw audio. Delete removes the file. Reprs and logs never include embeddings.
- Why: Fernet is simple and misuse-resistant for small blobs, and MultiFernet gives key rotation later. AESGCM needs nonce management.

## D-007 (2026-10-08) OpenAI Realtime adapter
- What: Use the GA Realtime API over WebSocket (`wss://api.openai.com/v1/realtime?model=...`, default model `gpt-realtime-2.1`, configurable, with no `OpenAI-Beta` header). Send `session.update` with `session.type="realtime"`, `session.audio.input.turn_detection=null`, and `audio/pcm` (24 kHz only), so the adapter resamples 16 kHz→24 kHz. Each accepted turn is sent as `[conversation.item.create input_text "[Speaker: X]" in collaboration mode]` → `input_audio_buffer.append`… → `input_audio_buffer.commit` → `response.create`. Output is `response.output_audio.delta`. Barge-in uses `response.cancel` plus `conversation.item.truncate`. The adapter is verified offline against a local fake WebSocket server. If the `openai` SDK is used, its realtime extra needs `websockets<16`.
- Uncertain: the exact `input_text` content shape for the attribution item. Verify it in the docs when implementing.
- Why: We own turn-taking (SPEC). Provider types never leave `adapters/`.

## D-008 (2026-10-08) ECAPA optional extra: pinned versions and workarounds
- What: extra `ecapa` = `torch==2.8.0`, `torchaudio==2.8.0`, `speechbrain==1.0.3` (imports cleanly on 3.12/aarch64 linux; torchaudio 2.8 is the last release that still has `list_audio_backends`, which speechbrain calls at import, so >= 2.9 is avoided). torch/torchaudio come from the PyTorch CPU index through `[tool.uv.sources]` (explicit index, linux/win32 markers; macOS uses PyPI wheels). Import emits harmless deprecation warnings.
- Workarounds: we bypass `EncoderClassifier`/Pretrainer (HF download, symlinks) and build `Fbank -> InputNormalization(sentence) -> ECAPA_TDNN` directly, loading only `embedding_model.ckpt` (rev-pinned, sha256-verified, Apache-2.0) into `models/`. Audio comes in as numpy, so no torchaudio I/O backend is used. `mean_var_norm_emb`/classifier are unused (as in `encode_batch` with normalize=False).
- Note: plain `uv run` (no `--extra ecapa`) removes torch from the venv, so the smoke SKIPs; use `uv run --extra ecapa` or `uv sync --extra ecapa`.

## D-009 (2026-10-08) Embedder and threshold
- What: default embedder **wespeaker-resnet34** (ONNX, no torch), cosine threshold **0.35** (ECAPA fallback 0.32), `MIN_MARGIN` 0, enrollment ≥ 10 s speech in 3 s windows / 1.5 s hop (5 LibriSpeech utterances in the bench), minimum decision length 1 s (`MIN_DECISION_S`; defined here, consumed by the M1 pipeline, not yet enforced). All in `voiceroom/config.py`; `Matcher(threshold=None)` and `enroll` read it; `make bench` reports at these thresholds.
- Numbers (`reports/bench-*.md`, LibriSpeech dev-clean, 30 convs, 960 target / 1920 non-target trials):
  - Clean EER: wespeaker **3.33 %**, ECAPA 4.71 %. ≥ 1 s EER: wespeaker 0.69 %, ECAPA 1.11 %.
  - Wespeaker at 0.35, clean, ≥ 1 s: **FAR 1.18 %** (target < 2 %), **FRR 0.28 %** (target < 5 %). Both met. (At the old EER point 0.299, ≥ 1 s FAR was 3.96 %, which misses; hence the higher threshold. Side runs with `--threshold` 0.38 / 0.42 gave ≥ 1 s FAR 0.49 % / 0.07 % and FRR 0.69 % / 1.94 %.) ECAPA at 0.32 (its clean 1 % overall-FAR point) also meets the clean targets (≥ 1 s FAR 1.25 %, FRR 1.11 %) but is worse on < 1 s (FRR 37.9 % vs 18.8 %) and 10 dB EER (11.46 % vs 10.10 %).
  - Short (< 1 s), clean, at 0.35: EER 7.08 %, FRR 18.75 %, FAR 0.42 %. Not covered by the targets; reported separately.
  - 10 dB white noise, at 0.35: overall FAR 1.46 %, FRR 28.44 %; ≥ 1 s FAR 1.88 %, **FRR 16.94 %**; ≥ 1 s EER 6.67 %.
  - Latency: p95 per-clip embedding 595 ms (p50 ~75 ms; clean run, includes first-call/long-clip outliers); RTF 0.060 (`reports/bench-wespeaker-resnet34.md`). ECAPA: p95 500 ms, RTF 0.056. Both are far below real time, but p95 ≈ 0.6 s eats into the early-decision budget.
- Why wespeaker: lower EER in every condition, no torch at runtime, 26 MB, comparable speed.
- Gap: the FA/FR targets are met for clean audio only. With 10 dB noise ≥ 1 s FRR is 16.9 % (> 5 %), and < 1 s FRR is high in all conditions. The p95 latency is also high. Follow-ups added: T-024 (noise robustness: score norm / multi-centroid / noisy enrollment), T-025 (p95 latency), T-026 (CAM++ comparison).
- Caveat: LibriSpeech is read, clean speech; the threshold should be re-checked on live mic audio (T-023).

## D-010 (2026-10-08) OpenAI Realtime wire details (settles D-007 uncertainty)
- What: raw `websockets` client (no `openai` SDK). Attribution item = `{"type":"message","role":"user","content":[{"type":"input_text","text":"[Speaker: X]"}]}` sent before append/commit. Audio is appended in 100 ms pcm16 LE 24 kHz chunks. Reply audio is emitted at 24 kHz (`AudioOut.sample_rate=24000`); the sink resamples. `conversation.item.truncate.audio_end_ms` is clamped to the received audio length.
- Why: fewer dependencies, and the fake server speaks the same JSON. The input_text shape follows the GA client-events reference (developers.openai.com/api/reference/resources/realtime/client-events).
- Alternatives: the `openai` SDK realtime client; a single item with `input_text` + `input_audio` (kept as a fallback if attribution turns out weak live).

## D-011 (2026-10-08) Noise / short-utterance variants (T-024)
- What: compared 8 scoring variants (`python -m voiceroom.bench.compare`, `reports/compare-wespeaker-resnet34.md`; wespeaker, LibriSpeech dev-clean, 30 convs, white noise at 10 dB). Each variant's threshold is calibrated on clean ≥ 1 s at FAR ≈ 1 %, then judged on 10 dB.
- Numbers (10 dB, ≥ 1 s FRR at FAR ≤ ~1 %): baseline 18.2 %; k-means 3 centroids 16.7 %; top-3 chunks 17.8 %; AS-norm 16.5 %; noise-aug enrollment 14.0 % (FAR 1.6 %); **noise-aug + AS-norm 12.4 % (FAR 0.97 %)**; noise-aug + top-3 + AS-norm 21.1 %. < 1 s 10 dB FRR: 72.5 % baseline → 58.3 % best.
- Wired behind config (all **off by default**): `ENROLL_NOISE_SNRS` (e.g. `(20, 10, 5)`; pink/brown noise, deliberately not the white noise used in testing) and `Matcher(cohort=...)` → AS-norm with `ASNORM_THRESHOLDS` (wespeaker 2.88).
- Target NOT met: best 10 dB ≥ 1 s FRR 12.4 % vs < 5 %. Off by default because gain is moderate, AS-norm needs a cohort file (not yet shipped/loaded by the pipeline), and enrollment costs 4x embeds.
- Caveats: one seed, ~720 ≥ 1 s targets so ±1-2 pt noise; cohort comes from the same corpus; noise is synthetic white.
- AS-norm scores are z-units: the 2.88 threshold holds only for a bench-like cohort, and IsolationPolicy's cosine-scale early buffers must be rescaled before it is enabled in the pipeline (T-027).
- Next: stronger levers are likely a noise-robust embedder (T-026 CAM++) or denoising front-end; re-check on live audio (T-023).

## D-012 (2026-10-09) CAM++ evaluated, not adopted (T-026)
- What: added `campplus-en-voxceleb` (3D-Speaker CAM++ `iic/speech_campplus_sv_en_voxceleb_16k`, sherpa-onnx ONNX export, 29.6 MB, 512-d, Apache-2.0 per the ModelScope card and the 3D-Speaker repo; VoxCeleb data terms still apply; sha256 pinned in `scripts/fetch_models.py`). Same 80-dim Kaldi fbank (povey window, [-1,1] samples, per-utterance mean norm). Registered and in `make bench`; report `reports/bench-campplus-en-voxceleb.md`. Threshold 0.376 in config (clean 1 % FAR point).
- Numbers (LibriSpeech dev-clean, same bench as D-009): clean EER 4.24 % (wespeaker 3.33 %); 10 dB EER 11.25 % (wespeaker 10.10 %). ≥ 1 s at its threshold: clean FAR 1.32 % / FRR 0.69 % (wespeaker 1.18 / 0.28); 10 dB FRR 16.81 % (wespeaker 16.94 %, i.e. no noise gain). Latency p95 ~83 ms vs wespeaker ~165 ms (RTF 0.009 vs 0.017); about 2x faster, but reports come from separate runs under varying machine load.
- Decision: wespeaker-resnet34 stays the default (D-009 unchanged); CAM++ does not beat it on accuracy or noise robustness. It is a faster fallback only if latency becomes binding. Not a lever for the noisy-FRR gap (T-024 follow-up stands).
- Caveat: one seed, same corpus as calibration; threshold not tuned beyond the clean 1 % FAR point.

## D-013 (2026-10-09) AS-norm cohort file + policy rescale; defaults stay off (T-027)
- What: `voiceroom.cohort.Cohort` (plain npz (unencrypted since T-034) npz, mode 0600, signature-store key: unit-norm embeddings only, no audio; plus embedder, AS-norm threshold, top-N, `score_scale`). `python -m voiceroom.bench.cohort` builds `data/cohort-<embedder>.npz` (wespeaker: 120 windows from 20 LibriSpeech dev-clean speakers; threshold calibrated at FAR 1 % on the other 20 speakers' 2 s clean probes = 3.90, FAR 1.02 %, TAR 98.8 %; score_scale 6.49 = 1/median cohort std). `voiceroom demo` loads the file when present (`--no-cohort` to skip) and uses its threshold unless `--threshold` is given. `Matcher(cohort=Cohort)` adopts threshold/top-N and exposes `score_scale`; Isolation/Collaboration policies multiply `early_score_buffer`, `early_margin`, `window_buffer`, `window_drop` by it (Pipeline calls `bind_matcher` on both). The cohort also records its speaker ids so the bench excludes them from its draw.
- Why the threshold moved from 2.88 (D-011) to 3.90: a smaller cohort (120 vs ~220) and 2 s clean probes; a cohort file is only valid with its own stored threshold.
- Defaults: the file is opt-in by presence (data/ is gitignored, so a fresh checkout stays on cosine scoring); `ENROLL_NOISE_SNRS` stays `()`. The live-audio check (T-023) is still pending a human, so neither is enabled on evidence from synthetic noise alone; noise-aug costs 4x enrollment embeds for a moderate gain (D-011).
- Caveats: cohort and bench share the dev-clean corpus (bench excludes the cohort speakers), so numbers are still somewhat optimistic; the z-scale rescale is the 1/std approximation.
- Bench, clean, no regression: pipeline bench with the continuity check relaxed (`--window-drop 1.0`, because at the default the cosine baseline commits 0/24 segments; T-028), same conversations (cohort speakers excluded from both): cosine 10 commits, owner FR 42.9 % (3/7), non-owner FA 0/17, collab attribution 70.8 % (17/24); AS-norm 9 commits, owner FR 42.9 %, FA 0/17, collab 70.8 % (`reports/pipeline-wespeaker-resnet34-wd1.md`, `...-asnorm-wd1.md`). Small sample (24 segments), so only "no visible regression". Score level: AS-norm TAR 98.8 % at FAR 1.02 % on 20 held-out speakers.
- score_scale is 11.6 with leave-one-speaker-out (6.5 when same-speaker windows stay in the cohort, which understated it).

## D-014 (2026-10-09) Continuity window_drop calibrated; 0.5 s windows are the limit (T-028)
- What: `python -m voiceroom.bench.windows` (reports `windows-<embedder>[-w32].md`) builds owner turns (3-6 s, one utterance crop, LibriSpeech dev-clean, 30 trials x 2 = 60 turns) and the same with a spliced interior interjection (0.5/1/2 s of an enrolled other or a stranger, >= 1 s of owner speech each side; 180 turns), scores the pipeline's windows and sweeps `window_drop` x `window_buffer`. Config `WINDOW_DROPS` wespeaker and ecapa: 0.05 -> **0.3**.
- Numbers (wespeaker, 0.5 s windows, buffer 0.1): drop 0.05 -> owner FR 100 %, leak 0 %; 0.15 -> FR 83 %, leak 0.6 %; **0.3 -> FR 65 %, leak 1.1 % (0.5 s: 3.3 %, >= 1 s: 0 %)**; 1.0 -> FR 63 %. FR does not fall below ~63 % even with the drop test off, and with no absolute floor and no drop (best-candidate check only) it is 30 % with leak 6 %: the absolute floor (threshold - buffer) and the `best == owner` check over 3 enrolled speakers on 0.5 s windows both reject owner windows (floor off: 30 % FR). Raising `window_buffer` to 0.2 at drop 0.3 gives FR 55 %, same leak 1.1 %, so buffer does matter. ecapa at buffer 0.1: FR 88 %, leak 0 %.
- With 1 s windows (`--win-frames 32`, wespeaker, buffer 0.1): drop 0.15 -> FR 28 %, leak of >= 1 s interjections 0 % (0.5 s ones 17 %); drop 0.2 -> FR 22 %, leak 1.7 % at 1 s. Much better, still far above a usable FR.
- Why 0.3: the knee at 0.5 s windows (beyond it FR gains nothing, leak starts to rise); 0.05 rejected every owner turn. Also matches what smoke_pipeline_real had to force.
- Not done / caveat: `window_buffer` kept at 0.1 (a policy-wide default, not per-embedder; 0.2 looks ~10 pt better for wespeaker but is 3.3 % leak for ecapa, so left for T-031). Bench has no VAD and does not measure the AS-norm (cohort) path. Real embedder, clean read speech, spliced (not overlapped) interjections, no VAD; the continuity check as designed is not viable for isolation FR targets, so treat the 0.3 as "least harmful", not good. Follow-up T-031 for longer windows.

## D-015 (2026-10-09) Continuity check rejects on a run of bad windows, not any bad window (T-029)
- What: `windows_ok` (isolation and collaboration) fails a turn only when `window_bad_run` consecutive windows are bad (owner not best, or score below the floor); unvoiced pause windows are `None` and break a run; a turn with fewer scored windows than the run needs fails if all are bad. Config `WINDOW_BAD_RUNS` wespeaker = 3 (ecapa/toy/unknown = 1, the old strict rule: ecapa not measured with runs); wespeaker `WINDOW_DROPS` 0.3 -> 0.4 (the drop is nearly irrelevant once runs are used: 0.3 and 0.4 rows identical); `window_buffer` stays 0.1. Segmenter `end_silence` unchanged (0.4 s: longer hangover costs commit latency one-for-one against the 700 ms target; split parts are each judged alone and did not drive FR).
- Why: D-014 showed 0.5 s windows of one speaker fail individually too often (FR >= 63 % with "any bad window"). Isolated failures are noise; a sustained foreign span is not. Offline sweep (`bench.windows --bad-run 3`, `reports/windows-wespeaker-resnet34-run3.md`, drop 0.4, buffer 0.1): owner FR 8.3 % (5/60), leak 1 s 3.3 %, 2 s 0 %, 0.5 s 60 %. Run 4 was tried: lower FR at buffer 0.15 but 1 s leak 15-27 %, rejected by the T-031 leak bar. A guard on "another enrolled speaker above threshold" did not help.
- Pipeline bench (14 conversations, 84 segments, `reports/pipeline-wespeaker-resnet34.md`): owner FR 4.3 % (1/23), non-owner FA 1.6 % (1/61), attribution 96.4 %, commit p95 433 ms. Marginal: 23 owner segments only, and the larger offline window bench says ~8 % FR for owner turns, so expect FR in the 4-8 % range.
- Caveat: interjections < ~1 s inside an accepted owner turn mostly leak (0.5 s: 60 %). Whole-turn rejection of other speakers is unaffected. Clean read speech, no overlap.
- Round 2 (reviewer FAIL): added a foreign-speaker guard (any window whose confident match is a *different enrolled* speaker rejects the turn), an all-scored-windows-bad rule that holds across pauses, and a standalone-safe `window_bad_run` fallback. Windows bench (run 3, drop 0.4, buffer 0.1): owner FR 10.0 % (6/60), leak 0.5 s 41.7 %, 1 s 3.3 %, 2 s 0 %, enrolled interloper 4.4 %, stranger 25.6 %. Pipeline bench unchanged: FR 4.3 % (1/23), FA 1.6 %, attribution 96.4 %. Strangers (below threshold for every enrolled speaker) cannot be caught by a guard; interior leak of short interjections is bounded only by the window size. Owner decision requested in `needs_human.md`.
- Owner decision (2026-10-09 12:51): ship the rule as the isolation default (3 bad windows in a row + foreign-enrolled guard, drop 0.4). Rejected: the old strict rule (owner FR 65 %, isolation unusable) and run 4 (83 % of 0.5 s interjections leak, 15-27 % at 1 s). Trade-off, windows bench (wespeaker, 60 owner turns, 180 interjection turns): owner FR 10.0 %; leak 0.5 s 41.7 %, 1 s 3.3 %, 2 s 0 %. Documented in README "Known limits". Follow-up T-032: 1 s windows / VAD-aware splitting; rerun the windows bench and require owner FR < 5 % with a lower 0.5 s leak.

## D-016 (2026-10-09) VAD-aware windows bench + deep-window rule (T-032)
- What: (1) `bench.windows` now runs SileroVAD like the pipeline (pause windows unscored, windows embed speech frames only; `--no-vad` restores the old bench). (2) New "deep window" rule in `windows_ok` (both policies): `DEEP_BAD_RUN` = 2 consecutive windows where the owner is not best and scores under threshold - `DEEP_BUFFER` (0.2) reject the turn; a clear foreign span needs fewer windows than the doubtful 3-run. Window width/hop (0.5 s / 0.25 s), run 3 and drop 0.4 are unchanged.
- Why: most of the old bench's owner FR (10 %) was pause windows the pipeline never scores. Rejected: 1 s windows (blur 0.5 s interjections: leak >= 53 % at similar FR); hop 0.125 s with run 5 (leak 30 %, but twice the window embeddings: commit p95 3 s+ / `identify_busy` drops under load, misses the 700 ms target).
- Result (`reports/windows-wespeaker-resnet34-run3.md`, buffer 0.1, drop 0.4, seed 0): owner FR 3.3 % (2/60), leak 0.5 s 38.3 %, 1 s 3.3 %, 2 s 0 %. Held-out seed 1: FR 1.7 %, 0.5 s 40.0 %, 1 s 10.0 %, 2 s 1.7 %. D-015 baseline (no VAD in bench): FR 10 %, 41.7 %, 3.3 %, 0 %. Gain is mostly FR; the 0.5 s leak improves only a few points: the limit is the window size.
- Caveat: the deep rule needs a rival to be "best", so it is inert when only the owner is enrolled (the bench enrolls 3).

## D-017 (2026-10-09) Short turns get a lenient continuity check (T-035)
- What: turns shorter than `CONTINUITY_MIN_S` (2.0 s, length incl. 0.2 s pre-roll, to end of speech) call `windows_ok(..., short=True)`. Isolation then rejects only on two consecutive windows naming a different enrolled speaker, or two consecutive windows under the long rule's score floor (`max(threshold - buffer, turn median - drop)`) whoever is best (so it works with only the owner enrolled; round 2 fix, the first version used a deep-only rule that leaked with owner-only enrollment). Collaboration keeps one named foreign window as a reject (attribution). Off for short turns: the doubtful 3-run, the single-foreign guard (isolation), the all-bad rule. Long turns unchanged (D-015/D-016). Threshold 0.35, drop 0.4, buffer 0.1 unchanged.
- Analysis: in the live log (T-023, `--no-cohort`) the alice turns dropped were 1.15 s, 1.54 s and 0.16 s long while identified as alice; the whole-turn match accepts, so the drop can only come from `windows_ok`. A 1.2-1.5 s turn has 3-4 half-second windows, so one odd window (or one confident "bob" window from mic/room mismatch with enrollment) trips the single-foreign guard or the all-bad rule; a 0.16 s turn is one sub-window slice. The log holds no window scores, so which rule fired is inferred, not measured. Offline clean LibriSpeech does not reproduce it: owner FR on 1-2 s turns 3.3 % (2/60), same as 3-6 s turns. Narrowband (300-3400 Hz, enrollment too, `bench.windows --narrowband`, buffer 0.1, run 3, drop 0.4): owner FR 10.0 % (3-6 s) / 5.0 % (1-2 s), leak 0.5 s 38 %, 1 s 13 %, 2 s 0 %, stranger 25.6 %. Caveat: narrowband runs enroll with 9 utterances vs 5 for clean, so the narrowband cost vs clean (~7 pt FR, ~10 pt 1 s leak) is if anything understated.
- Offline measurement (round 2: `bench.windows` now picks `short` like the pipeline via `is_short_turn` and has owner ~1 s + 0.5/0.75 s tail cases; clean wespeaker, 30 trials, run 3, drop 0.4, buffer 0.1): owner FR on 1-2 s turns 6.7 % (4/60) with the short rule (3.3 % with the old rule in the earlier run, noise-level at n=60, so NO clean-audio gain; the rationale rests on the live log). Short-tail leak (still accepted): 0.5 s tail enrolled 20 % / stranger 30 %, 0.75 s tail enrolled 3.3 % / stranger 20 %. Smoke covers owner-only enrollment (0.75 and 0.9 s tails rejected). Pipeline bench (14 convs, as D-015) is unchanged (FR 4.3 %, FA 1.6 %, attribution 96.4 %). Known cost: in isolation, a foreign tail <= ~0.5 s after ~1 s of owner speech inside a turn < 2 s is accepted (smoke_e2e_isolation: such tails accepted by design, 0.75 s tails rejected).
- Not done: threshold change either way (no live scores), live AS-norm check. Follow-up T-036: log which rule fired + window scores in the demo.

## D-018 (2026-10-09) M3 room architecture: multi-source mux, track identity verified by voice, plain LiveKit rtc
- What:
  - **Multi-source.** `RoomPipeline` runs one VAD and segmenter (`SourceProcessor`) per participant track, with a shared matcher and **one** provider. Accepted turns go through a commit queue: no `send_turn` interleaving, end-of-speech order.
  - **Identity.** A track's claimed identity (LiveKit participant identity / `voiceroom_user` attribute) is checked by a **1:1 voice verification** against that member's signature, using the lenient (short-turn) continuity rule. A confident match to another member counts as a mismatch, and a stranger counts as unknown. Shared-mic tracks fall back to the existing collaboration identification.
  - **Bleed.** A turn that is concurrent and quieter, and does not match its track's owner, is dropped as cross-talk bleed.
  - **Module layout.** Session membership drives the accepted set. The transport-agnostic interface lives in `voiceroom/rooms/`. LiveKit code lives in `voiceroom/adapters/livekit_*.py`, which keeps the existing "no provider imports outside adapters/" smoke rule.
  - **Testing tiers.** `FakeRoom` (in-memory) first, then a pinned local `livekit-server --dev` binary in `data/bin/` (localhost, offline). LiveKit Cloud or real devices come only in the final human task.
- Why: T-023 and D-014–D-017 showed that best-of-N voice identification on short real-mic turns causes owner false-rejects. With per-person mics, the track already says who should be speaking, so voice only has to *verify*. Verification is easier, and its errors are cheaper.
- Library: plain `livekit` (rtc) + `livekit-api` (1.1.x / 1.2.x as of 2026-10-09; py3 wheels for linux x86_64/aarch64 and macOS arm64), not `livekit-agents`. We own turn-taking (SPEC). The agents' OpenAI Realtime plugin runs its own turn detection, which conflicts with ours, and we already have our own adapter.
- Unverified, to be settled in T-044: whether `AudioStream(sample_rate=16000)` resamples (otherwise use our `StreamResampler` from 48 kHz), whether two rtc clients in one process work headless, whether localhost needs no TURN, and the exact ports. Python has no per-participant audio level, so we compute levels from our own frames. `active_speakers_changed` is available but not relied on.
- Alternatives: livekit-agents `AgentSession` (rejected above); one `Pipeline` + provider per track (rejected: several model sessions, no shared conversation); mixing all tracks into one stream (rejected: throws away track identity and adds overlap).
